# WattDesk 改版设计策略 v0.1

日期：2026-09-23  
用途：产品、设计、研发、售后共同讨论改版方向；作为后续信息架构和核心流程设计的输入。  
阶段：第一轮结构研究与设计建议，尚未进入完整 PRD、逐屏 UI 或最终排期。

## 1. 核心判断

建议将 WattDesk 定义为：面向业主、专业服务商和平台团队的多产品能源资产管理平台，覆盖设备接入、运行观察、策略控制、故障处理和资产交接。

改版主线：**统一业务对象 → 按角色与任务组织体验 → 用核心流程贯通现有功能 → 建立可扩展的多产品设计系统。**

推荐“一个产品底座、三类工作台、产品能力驱动的详情页”。三类工作台是体验分层，并不要求拆成三个独立 App 或三套代码。

- 业主工作台：了解自己的系统是否正常、能源如何使用、需要做什么、如何获得服务。
- 专业工作台：管理多客户、多站点，完成交付、监控、诊断和维护。
- 内部工作台：按职责处理技术支持、设备诊断、版本管理、平台运营和质量分析。

优先重构任务路径与对象关系，再决定视觉表现。页面数量不是唯一优化目标；更重要的是减少找入口、重复定位对象、理解状态和跨页面拼接信息的成本。

## 4. 用户划分：B/C 身份之外，还要按实际任务划分

同一个 B 端客户可能既是资产所有者，也是运维负责人；同一个人可能属于多个组织。不能只用注册时选择的 B/C 类型永久决定其全部能力。

| 使用者 | 首要任务假设 | 默认看到什么 | 主要入口 |
|---|---|---|---|
| 家庭业主/个人用户 | 确认正常、了解用能与费用、控制日常模式、找服务 | 当前状态、能源概况、可操作事项、服务联系人 | 业主 App；保留业主 Web 查看和管理能力 |
| 企业资产负责人 | 掌握资产运行表现和服务结果 | 站点表现、异常影响、趋势与报表 | 专业 Web 的资产管理视图 |
| 安装商/交付人员 | 建站、接入、配置、验收、交接 | 待交付任务、接入进度、配置检查 | 现场 App + Web 管理 |
| 服务商/运维人员 | 从多站中找到问题并处理 | 待处理事件、重点站点、负责范围 | 专业 Web + App 通知与现场处理 |
| 企业/渠道管理员 | 管理人员、客户关系和资源授权 | 组织、成员、角色、服务对象与授权 | 专业 Web 的管理区 |
| 内部技术支持 | 复现问题、读取证据、指导处理 | SN 搜索、设备上下文、日志、工单 | 内部服务工作台 |
| 研发/质量/平台运维 | 分析版本与故障、管控发布、观察平台健康 | 依职责开放的诊断、版本、质量、平台监控 | 内部工作台的独立权限区域 |

内部身份也不应默认获得所有客户资产的完整控制权限。访问范围应能追溯到支持任务、所属职责或有效授权。

## 5. 先统一业务对象，再画菜单

推荐对象模型：

```text
用户 ──组织成员关系/角色── 组织
用户或组织 ──所有权或访问授权── 站点
服务组织 ──服务关系/服务授权── 站点
站点 ──包含── 系统/设备组（按需要存在）── 设备 ──子部件
站点/设备 ──关联── 数据、事件、策略、命令、服务记录、变更历史
```

“站点”作为底层中性概念，可以按场景显示为电站、家庭系统或项目。独立加热器可以直接归属站点，不强迫用户建立一个名不副实的储能电站。“系统”用于表达确有控制或连接关系的一组设备，不为每台设备增加无意义层级。

需要明确的边界：

1. **账号、组织成员、客户关系、资产所有权是不同对象。** 删除成员不等于删除客户或设备；退出组织不自动转移资产。
2. **所有权与服务权限独立。** 更换安装商、增加临时服务方应有清晰流程。
3. **电站/站点与设备标识独立。** 换机后站点历史可延续，但旧设备数据、SN、保修和新设备数据不能混成同一台物理设备。
4. **连接状态、运行状态、健康状态、数据时效分开。** 在线不等于正常；离线不代表设备已停止运行。
5. **控制意图与实际状态分开。** 云端保存参数、命令发送、设备接收、应用参数、实际运行变化是不同阶段。
6. **组织切换是工作上下文。** 全局搜索、列表、报表、消息和批量操作均应明确当前范围，并由服务端执行权限检查。

权限建议按“角色 × 资源范围 × 操作 × 有效条件”定义。至少分别定义查看、导出、修改策略、设备控制、软件升级、成员管理、授权和资产转移；不能只通过隐藏按钮实现。

## 6. 信息架构建议

### 专业 Web：以工作台、资产、运维、分析、管理组织核心导航

| 一级入口 | 主要内容 | 边界 |
|---|---|---|
| 工作台 | 我的待办、重点异常、负责站点概况、最近访问、待交付 | 根据角色呈现；地图是可切换视图，不作为所有人的固定主角 |
| 资产 | 站点列表、设备列表、分组、接入/交接 | 同一资产模型的不同视图，避免做两套详情 |
| 运维 | 事件、告警、服务工单、操作任务 | 明确告警与工单的关系；是否需要完整工单模块由现有流程决定 |
| 分析 | 能源趋势、设备趋势、对比、报表、保存的分析视图 | 从站点/设备进入时保留对象和时间范围 |
| 管理 | 客户与服务关系、组织成员、角色授权、组织级配置 | 合并导航入口，不混淆底层业务对象 |

顶部保留组织/工作空间切换、SN/名称全局搜索、通知、帮助、个人设置。研发工具和平台运营配置放入独立内部区域，不扩大普通客户导航负担。

### 业主 App：以日常任务组织

建议初始结构：概览、能源、设备、服务；账户设置放个人入口。单设备且无能量分析能力的用户可采用更简单的入口组合，不留无意义空页。

概览依次回答：现在是否正常 → 能源/舒适状态如何 → 是否需要操作 → 当前模式与常用控制。

安装商 App 仍可使用同一应用内的工作身份，重点提供扫码接入、安装配置、现场检查、交付与告警处理。是否拆分独立 App，要根据账号体系、发布节奏和现场流程复杂度再决定。

### 站点和设备详情

站点详情建议统一骨架：概览 / 设备 / 能源与趋势 / 事件与服务 / 策略与设置 / 资料与授权。按角色和能力显示必要项，不要求每个站点都呈现六个标签。

设备详情共享身份、状态、数据时效、事件、配置和历史结构，专属内容按能力扩展：

| 产品 | 默认重点 | 专业下钻 | 不宜直接通用化的部分 |
|---|---|---|---|
| 电池 | SOC、充放电状态、关键温度和告警 | 模组/电芯电压温度、压差、均衡、诊断趋势 | 电芯结构、保护参数、不同代际能力 |
| 逆变器 | 能量流、当前模式、输入输出、运行状态 | 分相/回路、并网状态、策略与变更记录 | 地区电网规范、兼容性、参数依赖 |
| 加热器 | 当前/目标温度、加热状态、模式、用电来源 | 自检结果、负载类型、功率限制、控制策略 | 扰动策略、最低温度保障、型号专属功能 |

SOH、节费、备电时长、预测等信息仅在数据和模型足够可靠时提供，并注明口径或估算性质。不同设备的功率/电量汇总应先确认计量边界，避免重复计量。

## 8. 优先贯通的五条流程

### A. 新设备交付

创建/选择客户与站点 → 扫码或输入 SN → 验证归属及兼容性 → 接入网络/网关 → 必要配置 → 检查遥测与运行状态 → 交付业主 → 建立服务授权。

要求：显示步骤与阻塞原因；支持保存进度；区分已登记、已绑定、已联网、已上报、已投运。处理中断不能强制从头输入。已被其他主体绑定的设备提供正规的转移/联系服务路径。

### B. 异常发现到恢复

收到通知/工作台发现 → 确认影响对象和严重程度 → 查看事件时间线和相关趋势 → 分配或接手 → 远程诊断/现场处理 → 确认设备恢复 → 完成服务记录。

要求：区分已读、已确认、已分配、已恢复、已关闭；故障自然恢复与工单完成分别表达。一个通信中断可能产生多个衍生告警，可按规则分组，未经验证不能自动宣称根因。优先建立可理解的处理闭环，再评估复杂工单自动化。

### C. 策略或参数修改

查看实际状态与现行配置 → 选择目标/模式 → 编辑受支持参数 → 校验依赖与冲突 → 展示变更摘要及预计影响 → 下发 → 跟踪回执与生效状态 → 留存记录。

要求：明确草稿、待发送、已发送、设备确认、已应用、失败、超时等状态；具体枚举以协议能力为准。没有设备证据时不得显示“已生效”。在线/离线、固件支持、控制来源、已有任务影响可操作性。批量配置先校验适用设备，部分失败提供可追踪结果，重试避免重复危险操作。

普通用户从“优先自用、保留备电、按电价运行、保证热水”等目标理解策略；专业参数由具备权限的人员展开。提供哪些目标取决于实际控制能力，不承诺目前尚不支持的自动化。

### D. 客户交接和服务组织变更

选择资产和接收方 → 明确所有权/服务权类型 → 展示范围与影响 → 完成必要确认 → 更新关系 → 验证新旧权限 → 保留记录。

要求：所有权转移、添加只读访问、委托服务、撤销安装商权限是不同流程。跨组织可见范围不能因为一封联系邮箱或一个共享账号而含糊。

### E. 换机、维修与退役

定位旧设备及故障 → 建立服务记录 → 校验新设备 → 迁移适用配置 → 确认接入及数据 → 标记旧设备状态 → 完成交接。

要求：维护新旧 SN 关联、换机时间点、计量连续性说明和保修关系；不可自动假设不同型号所有配置都能复制。历史趋势明确分段。

## 9. 交互和 UI 的设计要求

### 信息层级

- 第一层：结论——系统是否正常、是否需要处理。
- 第二层：解释——影响、原因线索、重要变化。
- 第三层：证据——曲线、详细参数、日志。
- 第四层：行动——在明确上下文与权限下进行处理。

专业页面允许高信息密度，但必须有默认重点；业主页面以少量清晰结论和常用操作为主。不要把所有指标一律变成卡片。

### 共用交互规则

1. 列表支持搜索、过滤、合理默认列、保存视图和批量操作；进入详情后返回时保留筛选、排序和位置。
2. 地图服务于区域维护和地理定位，列表服务于对比和批量处理；同一数据范围可切换视图。
3. 轻量预览使用侧栏，复杂配置或多步骤工作使用完整页面；避免多层弹窗。
4. 告警通知直接到对应对象和事件；消息中心与设备事件使用同一状态来源。
5. 一般保存、涉及运行的控制、资产转移等操作采用不同反馈与确认强度。
6. 低频高级功能按角色与任务渐进展开，并提供稳定的专业入口和搜索，不把入口藏在无法发现的位置。

### 数据表达

- 显示最后更新时间和数据时效；区分实时遥测、汇总值、推算值和缺失数据。
- 区分 0、暂无数据、未安装、不支持、无权限、连接中断，不能统一显示为横杠或 0。
- 区分 kW 与 kWh、充电/放电、购电/售电方向，明确定义单位和正负值。
- 图表共享时间范围、采样粒度、时区和颜色语义；缺失数据留空或标识，不能默认为零或随意连线。
- 允许从告警时间定位相关曲线；用户操作、升级和换机可作为图表事件标记。
- 对比曲线仅合并具有可比较含义的量；多单位采用明确的轴与标签，必要时拆图。
- 报表注明统计区间、站点时区、汇总方式、数据完整性和估算口径。跨时区报表明确采用统一时间还是各站点本地日。

### 视觉系统

建立基础字体、字号、间距、边框、层级、交互与语义色规范，再形成数据表格、指标、能量流、曲线、告警、设备状态、命令进度和授权面板等业务组件。

品牌色与告警色分离；状态使用文字/图标/颜色共同表达。品牌主题可以更换 Logo 与主色，故障和成功等语义保持一致。支持长文本、本地化日期数字、不同单位和键盘操作。

能量流优先表达来源、去向、方向、功率和数据时效。动画只辅助理解；数据过期时应停止或明确标记，不营造系统仍在实时运行的误解。

设计系统必须覆盖加载、空状态、失败、无权限、离线、部分成功、操作进行中等状态。深浅色主题和大屏模式由真实使用环境决定优先级。

## 10. Web 与 App 分工

| 任务 | Web 重点 | App 重点 |
|---|---|---|
| 多站管理 | 列表、筛选、分组、对比、批量管理 | 关注站点、快速检索、现场定位 |
| 接入交付 | 客户/项目资料、批量准备、交付管理 | 扫码、网络接入、现场调试、验收；本地连接依硬件能力 |
| 数据分析 | 多曲线、长时间范围、跨设备对比、导出 | 当前状态、近期变化、易理解的趋势 |
| 运维服务 | 告警队列、证据整理、远程诊断、分配 | 推送、认领、检查清单、现场记录 |
| 日常控制 | 策略编辑、计划、配置追踪 | 少量高频控制、反馈、快捷模式 |
| 组织与授权 | 成员、角色、复杂范围管理 | 接受邀请、查看/撤销本人授权等必要操作 |

分工不意味着互相排斥。核心概念、状态与权限一致，围绕设备和工单的链接可以跨端接续。现场弱网时明确本地、云端和缓存数据来源，是否支持离线完成须由技术能力决定。

## 12. 客户需求如何验证

首轮建议邀请约 12–18 位代表用户，覆盖业主、安装交付人员、多站服务商、企业资产负责人及内部支持/研发。这个数量只用于发现主要任务与问题，不代表统计意义上的市场结论。再用行为数据和更大范围反馈确认普遍性。

优先收集最近 1–3 个月的售后问题分类、功能使用、失败操作、设备/站点数量分布和各端使用比例。在授权和数据最小化前提下使用真实任务材料。

访谈与观察重点：

1. 上次登录为了完成什么，最终在哪里完成？是否需要转到聊天软件或表格？
2. 上次设备异常时，怎么发现、如何判断影响、谁负责、如何确认恢复？
3. 一次新安装从扫码到业主可见有哪些阻塞点？
4. 什么参数最常修改？修改后怎样知道生效？
5. 安装商、经销商和业主发生交接时，哪些关系最难解释？
6. 哪些报告与信息必须保留，哪些只是很少使用的历史需求？
7. 加热器、电池、逆变器是否常在同一站点共存？哪些场景是独立设备？

低保真测试至少覆盖：发现最需要处理的站点、定位设备异常、改一个受支持策略并确认执行、完成交付授权、查看一台独立加热器。

关键指标建议：

| 目标 | 可测量指标 | 使用注意 |
|---|---|---|
| 更容易找到问题 | 任务成功率、定位首个需处理对象的用时、无效跳转 | 用同任务比较新旧版 |
| 接入交付更顺畅 | 首次成功率、中断恢复率、到首次有效数据的时间 | 区分界面、网络和硬件因素 |
| 控制更可理解 | 用户正确判断执行状态的比例、重复下发率、失败恢复率 | 云端响应时间不能替代设备生效时间 |
| 服务闭环更高效 | 确认/接手用时、远程解决比例、重复告警负担 | 故障类型与人员配置也影响结果 |
| 权限更清晰 | 正确配置授权比例、交接任务成功率、权限误解次数 | 测试跨组织和撤销场景 |
| 视觉与组件更统一 | 核心页面覆盖、状态覆盖、品牌差异复用情况 | 不把组件数量当成功指标 |

先建立基线，再制定数值目标。对于权限和高风险设备控制，测试中不可出现关键误操作；发现一次就应分析流程或提示是否失效。

## 13. 分阶段落地

### 阶段 0：建立共识与现状基线

交付物：有效页面/功能清单、旧稿与线上差异、角色任务矩阵、对象关系图、权限矩阵、产品能力矩阵、问题证据清单。

页面清单字段：现行版本、适用角色、所属对象、使用频率、业务价值、风险、前后置关系、线上状态、证据链接、保留/合并/迁移/退役建议。低频功能不能仅因低频删除，需检查法规、售后和少量高价值客户需求。

### 阶段 1：验证信息架构与关键流程

交付物：专业 Web 与业主 App 导航、站点/设备详情结构、五条核心流程的低保真原型、异常与权限状态设计、第一轮可用性测试结果。

通过条件：代表用户能够找到入口、理解对象关系和状态，核心任务能独立完成，研发确认遥测与命令反馈可实现。

### 阶段 2：首批闭环与设计系统

建议首批：角色工作台、站点/设备列表、统一详情骨架、基本事件处理、策略执行反馈、必要授权、业主概览，以及这些页面用到的共用组件。

复杂报表、全面批量升级、完整工单编排、自定义仪表盘、AI 策略与 3D 可视化按验证结果后置。若这些能力已在线且承担关键业务，应保留可达路径并分步迁移，不能简单下线。

### 阶段 3：扩展与迁移

交付物：产品专属诊断、换机流程、跨站分析、品牌配置、专业维护能力；旧链接映射、权限迁移、数据口径校验、试点与回退方案。

先按组织/角色/设备组合选取试点，观察新旧指标；客户资产标识和关键深链保持可追踪。迁移时特别检查既有授权、通知订阅、自动报告、时区和设备历史连续性。

阶段时长需在现状盘点后根据团队、协议与数据能力估算，本轮不将研究建议写成固定开发承诺。

## 14. 进入详细设计前需要明确的五个问题

1. 下一阶段首要业务目标是什么：降低售后成本、提升交付效率、增强业主体验，还是支持更多产品/OEM？先确定第一优先级。
2. 专业客户中主要是安装商、经销商、企业业主还是第三方运维？他们的典型站点规模和地区是什么？
3. 五类核心关系如何生效：资产所有权、组织成员、客户关系、服务授权、内部支持访问？
4. 产品真实能力边界是什么：遥测、下发回执、离线操作、固件兼容、联合控制与计量覆盖？
5. 哪些品牌差异必须保留，哪些是历史复制导致的视觉或交互不一致？

建议第一次评审先决定以上问题，并确认“对象关系图、角色任务矩阵、信息架构、核心流程”四项方向。确认后，再做首页、详情页和 App 的完整视觉稿。
